## 网络基础

### Q1: 描述 TCP 三次握手的过程

TCP 三次握手是建立连接的必经过程，目的是确认双方的收发能力都正常。

```
客户端                          服务端
  |                               |
  |--- SYN (seq=x) ------------>|  ① 客户端：我要连你
  |                               |
  |<-- SYN+ACK (seq=y, ack=x+1)-|  ② 服务端：收到了，我也准备好了
  |                               |
  |--- ACK (ack=y+1) ---------->|  ③ 客户端：好的
  |                               |
  连接建立，双方进入 ESTABLISHED
```

- **第一次握手**：服务端确认客户端发送正常，服务端接收正常
- **第二次握手**：客户端确认双方的收发都正常
- **第三次握手**：服务端确认客户端的接收正常，自己的发送正常

**为什么是三次？** 两次不够（服务端无法确认客户端是否收到自己的 SYN+ACK），四次多余（第三次握手后双方都已确认连通正常）。

### Q2: 描述 TCP 四次挥手的过程

```
客户端                          服务端
  |                               |
  |--- FIN (seq=u) ------------>|  ① 客户端：我发完了，想关了
  |                               |
  |<-- ACK (ack=u+1) ----------|  ② 服务端：知道了（半关闭，服务器可能还有数据要发）
  |                               |
  |<-- FIN (seq=v, ack=u+1) ---|  ③ 服务端：我也发完了
  |                               |
  |--- ACK (ack=v+1) ---------->|  ④ 客户端：好的
  |                               |
  TIME_WAIT (2MSL)               CLOSED
```

**TIME_WAIT 为什么是 2MSL？** MSL（Maximum Segment Lifetime）是报文最大存活时间。等待 2MSL 确保：
1. 最后一个 ACK 有足够时间到达服务端（如果丢了，服务端会重传 FIN）
2. 本次连接的所有报文从网络中消失，不会干扰新连接

**CLOSE_WAIT 过多**：说明服务端收到 FIN 后没有主动调用 close()，通常是代码逻辑问题。

### Q3: TCP 和 UDP 有什么区别？

| | TCP | UDP |
|------|-----|-----|
| 连接 | 面向连接（三次握手） | 无连接 |
| 可靠性 | 可靠传输（确认+重传+排序） | 不可靠（尽力而为） |
| 顺序 | 保证有序 | 不保证 |
| 流量控制 | 有（滑动窗口、拥塞控制） | 无 |
| 头部大小 | 20 字节 | 8 字节 |
| 适用场景 | HTTP、数据库、文件传输 | 视频直播、VOIP、DNS、游戏 |

**为什么 DNS 用 UDP？** 请求-响应报文小（通常 < 512 字节），UDP 开销低、一次往返即可完成。如果响应超过 512 字节则转为 TCP。

## HTTP 协议

### Q4: HTTP 和 HTTPS 有什么区别？

| | HTTP | HTTPS |
|------|------|-------|
| 端口 | 80 | 443 |
| 加密 | 明文传输 | TLS/SSL 加密 |
| 证书 | 不需要 | 需要 CA 签发 |
| 安全性 | 可被中间人窃听篡改 | 端到端加密 |
| 性能 | 较快 | 多 TLS 握手开销 |

**TLS 握手过程（简化）**：
1. 客户端发送支持的加密算法列表 + 随机数
2. 服务端返回选择的算法 + 证书（含公钥） + 随机数
3. 客户端验证证书，生成 pre-master secret，用公钥加密发给服务端
4. 双方用三个随机数生成对称会话密钥，后续通信全部用此密钥加密

### Q5: HTTP 的幂等性是什么？哪些方法是幂等的？

幂等性：对同一资源执行多次相同请求，结果与执行一次相同。

| 方法 | 幂等 | 说明 |
|------|------|------|
| GET | ✓ | 只读查询 |
| PUT | ✓ | 全量替换（执行多次结果一致） |
| DELETE | ✓ | 删除（第一次返回 200，后续返回 404，资源状态相同） |
| POST | ✗ | 创建资源（每次创建新的） |
| PATCH | 不一定 | 取决于实现 |

```python
# POST：非幂等
POST /users  # 每次都创建新用户
{"name": "张三"}

# PUT：幂等
PUT /users/1  # 无论执行几次，最终状态一样
{"name": "张三", "age": 25}
```

### Q6: 常见 HTTP 状态码有哪些？

| 状态码 | 含义 |
|--------|------|
| 200 OK | 请求成功 |
| 201 Created | 资源创建成功（POST 返回） |
| 204 No Content | 成功但无返回体（DELETE 后常用） |
| 301 Moved Permanently | 永久重定向 |
| 302 Found | 临时重定向 |
| 304 Not Modified | 缓存未修改（协商缓存） |
| 400 Bad Request | 请求参数错误 |
| 401 Unauthorized | 未认证 |
| 403 Forbidden | 无权限 |
| 404 Not Found | 资源不存在 |
| 405 Method Not Allowed | 请求方法不支持 |
| 429 Too Many Requests | 触发限流 |
| 500 Internal Server Error | 服务端内部错误 |
| 502 Bad Gateway | 网关/代理收到无效响应 |
| 503 Service Unavailable | 服务暂时不可用 |

## 网络安全

### Q7: XSS 和 CSRF 是什么？如何防范？

**XSS（跨站脚本攻击）**：攻击者往页面注入恶意脚本，当其他用户访问时脚本执行，窃取 cookie 或篡改页面。

```html
<!-- 反射型 XSS：参数未转义直接拼接进 HTML -->
<!-- URL: /search?q=<script>alert('xss')</script> -->
<div>搜索结果：<script>alert('xss')</script></div>
```

**防御**：
- 输出时对 HTML 实体转义（`<` → `&lt;`）
- 设置 Cookie 为 HttpOnly（JS 无法读取）
- 使用 CSP（Content-Security-Policy）头限制脚本来源

**CSRF（跨站请求伪造）**：利用用户已登录的身份，诱导用户点击链接触发恶意请求。

```
用户登录了 bank.com → 访问黑客的页面 → 黑客页面发起请求 bank.com/transfer?to=hacker&amount=10000
→ 浏览器自动带上 bank.com 的 cookie → 转账成功
```

**防御**：
- CSRF Token（表单中嵌入随机 token，服务端验证）
- SameSite Cookie（`SameSite=Strict` 或 `SameSite=Lax`）
- 关键操作二次验证（输入密码、短信验证码）
- 验证 Referer / Origin 头

### Q8: 密码应该怎么安全存储？

```
用户密码
   ↓
加盐哈希（每个用户独立的随机盐）
   ↓
bcrypt / scrypt / argon2（慢哈希，防暴力破解）
   ↓
存到数据库：$2b$12$salt+hash
```

**演化路径**：
- ❌ 明文存储
- ❌ MD5 / SHA1 / SHA256（计算太快，彩虹表一秒破解）
- ❌ MD5 + 固定盐（一个盐被破解就全库泄露）
- ✅ bcrypt + 随机盐（每次不同的盐，计算慢，防彩虹表也防暴力破解）

```python
import bcrypt

# 注册
password = "user_password"
hashed = bcrypt.hashpw(password.encode(), bcrypt.gensalt())
# 存到数据库：hashed.decode()

# 登录
bcrypt.checkpw(password.encode(), stored_hash.encode())
```

## 系统设计基础

### Q9: 什么是 C10K 问题？如何解决？

C10K（Client 10,000）问题指单台服务器如何同时处理 10,000 个客户端连接。传统模型为每个连接创建一个线程/进程，一万个连接意味着一万个线程，上下文切换和内存开销根本扛不住。

**解决方案演进**：
1. **多进程/线程 + 阻塞 I/O**：最早的方案，连接数上去就崩
2. **I/O 多路复用**：select → poll → epoll / kqueue，单线程管理所有连接
3. **Reactor 模式**：事件驱动的非阻塞模型（Nginx 就是这个思路）
4. **协程**：Go 的 goroutine、Python 的 asyncio，写起来像同步但底层是异步

```
C10K 已不是问题。现代 Linux + epoll + 合理架构，单机扛百万连接也不是难事（C10M）。
重点已经从"怎么扛住连接数"转到"怎么高效处理业务逻辑"。
```

### Q10: RESTful API 设计原则有哪些？

1. **用名词表示资源**：`/users` 不是 `/getUsers`
2. **HTTP 方法表示操作**：GET（查）、POST（增）、PUT/PATCH（改）、DELETE（删）
3. **资源层级嵌套**：`/users/1/orders/2`（不超过两层，太深用 query 参数）
4. **状态码语义化**：201 创建成功，204 删除成功，400 参数错，404 不存在
5. **版本化**：`/api/v1/users` 或 Header `Accept: application/vnd.api.v1+json`
6. **分页、过滤、排序**：`/users?page=2&limit=20&sort=-created_at`

```python
# 用 FastAPI 举例
from fastapi import FastAPI

app = FastAPI()

@app.get("/api/v1/users/{user_id}")       # 查
@app.post("/api/v1/users")                 # 增
@app.put("/api/v1/users/{user_id}")        # 改（全量）
@app.patch("/api/v1/users/{user_id}")      # 改（部分）
@app.delete("/api/v1/users/{user_id}")     # 删
```

### Q11: 什么是浏览器缓存策略？

**强缓存**：不发请求，直接用本地缓存。
- `Cache-Control: max-age=3600`（相对于请求时间，3600 秒内有效）
- `Expires: Thu, 01 Dec 2022 16:00:00 GMT`（绝对时间，有客户端时钟偏差问题）

**协商缓存**：发请求，服务端判断资源是否变化，没变化返回 304 Not Modified。
- `Last-Modified` / `If-Modified-Since`：基于时间
- `ETag` / `If-None-Match`：基于内容哈希（更精确）

```
请求 → 强缓存命中？ → 直接用
       ↓ 未命中
     发请求 → 服务端返回 304？ → 用缓存
              ↓ 返回 200
             用新资源并更新缓存
```

## Web 服务器与网关

### Q12: CGI 和 WSGI 是什么？有什么区别？

| | CGI | WSGI |
|------|-----|------|
| 全称 | Common Gateway Interface | Web Server Gateway Interface |
| 定位 | 通用标准，语言无关 | Python 专用（PEP 3333） |
| 进程模型 | 每次请求 fork 新进程 | 常驻进程，复用 |
| 性能 | 差（每次启动新进程） | 好（进程复用） |

**WSGI 规范**要求应用是一个可调用对象，接收 `environ`（环境变量字典）和 `start_response`（回调函数），返回可迭代的响应体。

```python
# 最简单的 WSGI 应用
def simple_app(environ, start_response):
    status = '200 OK'
    headers = [('Content-Type', 'text/plain')]
    start_response(status, headers)
    return [b'Hello World']
```

**常见 Python WSGI 服务器**：Gunicorn（fork + sync/async worker）、uWSGI（C 实现）、Waitress（纯 Python）。

### Q13: Nginx 和 Apache 有什么区别？

| | Nginx | Apache |
|------|-------|--------|
| 架构模型 | 事件驱动、异步非阻塞 | 进程/线程 per 连接 |
| 并发处理 | 单 worker 可处理数千连接 | 连接多了内存暴涨 |
| 静态文件 | 极快 | 较慢 |
| 动态内容 | 反向代理到后端 | 可用 mod_php 直接在进程内处理 |
| 配置 | 简洁直观 | .htaccess 灵活但影响性能 |
| 反向代理 | 核心功能 | 需要模块 |

**实际部署中常见的组合**：Nginx 在前做反向代理和静文件服务，Gunicorn/uWSGI 在后运行 Python 应用。Nginx 扛住万级连接，后端只处理"有业务的请求"。
