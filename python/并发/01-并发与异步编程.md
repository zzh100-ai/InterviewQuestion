## 并发和并行

### 并发和并行的区别？

- 并发：多个任务在**同一时间段内交替执行**，宏观上同时进行，微观上可能是串行
- 并行：多个任务在同一时刻真正实现同时执行，必须依赖多喝CPU

### python中实现并发的主要方式有哪些？

- 多线程
- 多进程
- 协程
- 一些高级接口

## GIL 全局解释器锁

### 什么是 GIL？它有什么影响？

GIL（Global Interpreter Lock）是 CPython 解释器中的一把全局互斥锁，它保证同一时刻只有一个线程在执行 Python 字节码。即使运行在多核 CPU 上，多线程也无法真正并行。

**核心影响**：

* **CPU 密集型任务**：多线程性能不会提升，反而因为因上下文切换和锁竞争降低效率
* **I/O 密集型任务**：GIL 在 I/O 等待时会释放，多线程可以获得明显性能提升

```python
# CPU 密集型：多线程没有优势
import threading
import time

def cpu_bound():
    total = 0
    for i in range(10_000_000):
        total += i

# 两个线程跑 CPU 密集任务，总时间约等于串行
```

**为什么 GIL 存在？**

CPython 的内存管理（引用计数）不是线程安全的。如果每个线程都能同时修改引用计数，会出严重的内存问题。GIL 是保护解释器内部状态最简单的方式。

**规避方案**：

* 多进程（multiprocessing）：每个进程有独立的 GIL
* 协程（asyncio）：单线程异步，不受 GIL 约束
* C 扩展：在 C 代码中手动释放 GIL
* 其他实现：Jython（无 GIL）、PyPy（有 GIL 但 JIT 部分弥补）

### 什么时候用多线程，什么时候用多进程？

| 场景 | 方案 | 原因 |
|------|------|------|
| I/O 密集型（网络请求、文件读写、数据库查询） | 多线程 / 协程 | GIL 在 I/O 等待时释放 |
| CPU 密集型（数值计算、图像处理） | 多进程 | 绕过 GIL 限制 |
| 高并发网络服务 | 协程（asyncio） | 单线程高并发，切换开销极小 |
| 需要共享大量数据 | 多线程 | 线程间共享内存，进程间需要序列化 |

```python
from concurrent.futures import ThreadPoolExecutor, ProcessPoolExecutor

# I/O 密集 → 线程池
with ThreadPoolExecutor(max_workers=10) as pool:
    results = pool.map(fetch_url, urls)

# CPU 密集 → 进程池
with ProcessPoolExecutor(max_workers=4) as pool:
    results = pool.map(heavy_compute, data)
```

### 如何克服 GIL 的限制？

- 使用多进程，每一个进程有独立的GIL
- 使用 C 扩展释放 GIL
- 使用其他 python 解释器
- 使用 `asyncio` 处理高并发`I/O`

### `threading` 模块中 Lock 和 RLock 的区别是什么？

- Lock：基于互斥锁，同一线程只能获取一次，重复获取会造成死锁，并且任何线程都可以调用`re
- RLock（可重入锁）：允许同一线程允许同一线程多次获取，内部维护计数器和持有线程信息，每次 `release()` 减少计数，直到为零才真正释放。

> 死锁

```python
import threading

lock=threading.Lock()

def func(n):
    lock.acquire()
    print(f"第{n}次获取锁")
    try:
        if n>0:
            func(n-1)
    finally:
        lock.release()

func(3)
```



### 解释死锁发生的条件，在python中如何避免

死锁的四个必要条件：互斥、持有并等待、不可剥夺、循环等待。

- 使用 `RLock` 避免自身重入死锁
- 使用超时锁获取（`lock.acquire(timeout=...)`）
- 使用上下文管理器（`with lock:`）确保释放
- 避免嵌套锁，设计一致的获取顺序
- 使用 `threading.Condition`、`Event` 替代复杂锁结构

### `threading` 的 `Event`、`Condition`、`Semaphore` 分别用于什么场景？

- `Event`：简单的线程间信号通知，一个线程等待事件发生，另一个线程设置事件。
- `Condition`：更复杂的条件变量，支持等待/通知，常与锁配合实现生产者-消费者模型。
- `Semaphore`：控制对有限资源的并发访问数量，如限制最大连接数。

## 多线程与多进程

### Python 中多线程如何实现？有哪些同步机制？

**创建线程**：

```python
import threading

# 方式一：传入目标函数
def worker(name):
    print(f"{name} 工作中")

t = threading.Thread(target=worker, args=("张三",))
t.start()
t.join()  # 等待线程结束

# 方式二：继承 Thread 类
class MyThread(threading.Thread):
    def run(self):
        print("自定义线程逻辑")

MyThread().start()
```

**常用同步机制**：

| 机制 | 用途 |
|------|------|
| `Lock` | 互斥锁，保护临界区 |
| `RLock` | 可重入锁，同一线程可多次获取 |
| `Semaphore` | 信号量，限制同时访问资源的线程数 |
| `Event` | 事件，线程间简单通知 |
| `Condition` | 条件变量，更复杂的等待/通知 |
| `Queue` | 线程安全队列，生产者 - 消费者模式 |

```python
import threading

# Lock 示例
lock = threading.Lock()
counter = 0

def increment():
    global counter
    for _ in range(100000):
        with lock:  # 上下文管理器自动 acquire/release
            counter += 1
```

### multiprocessing 中进程间如何通信？

进程间内存不共享，需要专门的通信机制：

```python
from multiprocessing import Process, Queue, Pipe, Value, Array, Manager

# 1. Queue：多生产者多消费者
q = Queue()
q.put("data")
item = q.get()

# 2. Pipe：点对点双向通信
parent_conn, child_conn = Pipe()
parent_conn.send("hello")
msg = child_conn.recv()

# 3. 共享内存（Value / Array）
counter = Value('i', 0)      # 共享整数
arr = Array('d', [1.0, 2.0]) # 共享数组

# 4. Manager：共享复杂对象
with Manager() as manager:
    shared_dict = manager.dict()
    shared_list = manager.list()
```

>`Queue` 和 `Pipe` 内部数据会被 pickle 序列化，频繁传大对象要注意性能。

### Q5: 线程池和进程池怎么使用？

`concurrent.futures` 模块提供统一接口：

```python
from concurrent.futures import ThreadPoolExecutor, ProcessPoolExecutor, as_completed

# submit 提交单个任务
with ThreadPoolExecutor(max_workers=5) as executor:
    future = executor.submit(pow, 2, 10)
    print(future.result())  # 1024

# map 批量提交
with ThreadPoolExecutor() as executor:
    results = executor.map(pow, [2, 3, 4], [10, 5, 3])
    print(list(results))  # [1024, 243, 64]

# as_completed：哪个先完成先处理哪个
with ThreadPoolExecutor() as executor:
    futures = {executor.submit(fetch, url): url for url in urls}
    for future in as_completed(futures):
        url = futures[future]
        result = future.result()
```

## 协程与 asyncio

### Q6: 什么是协程？和线程有什么区别？

协程是用户态的轻量级并发单元，调度完全由程序自己控制，不需要操作系统介入。

| 对比维度 | 协程 | 线程 |
|----------|------|------|
| 调度者 | 用户态 / 事件循环 | 操作系统内核 |
| 切换开销 | 极小（函数调用级别） | 较大（系统调用 + 上下文切换） |
| 内存开销 | KB 级别 | MB 级别（每个线程独立栈） |
| 并发数量 | 数万到数十万 | 数百到数千 |
| 数据共享 | 无竞态问题（单线程） | 需要锁保护 |
| 阻塞 | 只有 await 处让出 | 任意位置可能被抢占 |

```python
import asyncio

async def fetch_data(url):
    print(f"开始获取 {url}")
    await asyncio.sleep(1)  # 模拟 I/O，这里让出控制权
    print(f"完成获取 {url}")
    return f"数据来自 {url}"

async def main():
    # 并发执行多个协程
    results = await asyncio.gather(
        fetch_data("A"),
        fetch_data("B"),
        fetch_data("C"),
    )
    print(results)

asyncio.run(main())
# 三个协程并发执行，总耗时约 1 秒而非 3 秒
```

### Q7: async/await 的原理是什么？

`async def` 定义一个协程函数，调用它返回一个协程对象，不会立即执行。`await` 将控制权交还给事件循环，让其他协程运行。

```python
async def demo():
    print("第一步")
    await asyncio.sleep(0)  # 主动让出
    print("第二步")

# 本质上是将协程包装成 Task，放入事件循环调度
async def main():
    task1 = asyncio.create_task(demo())
    task2 = asyncio.create_task(demo())
    await task1
    await task2
```

事件循环内部维护一个就绪队列，当协程遇到 `await` 时：

1. 当前协程暂停
2. 事件循环找到下一个可以执行的协程
3. 被 await 的 Future 完成时，原协程回到就绪队列

### Q8: asyncio 中的 Task、Future、Coroutine 有什么区别？

| 概念 | 说明 |
|------|------|
| **Coroutine** | `async def` 定义的协程函数返回的对象，是最基本的执行单元 |
| **Future** | 表示一个 " 将来会有结果 " 的占位符，低层级 API |
| **Task** | Future 的子类，包装一个协程并在事件循环中调度执行 |

```python
# Coroutine：惰性的，不调度就不会执行
coro = my_coroutine()

# Task：立即被事件循环调度
task = asyncio.create_task(my_coroutine())

# 手动创建 Future
loop = asyncio.get_event_loop()
future = loop.create_future()
```

日常开发中直接用 `asyncio.create_task()` 创建 Task，用 `asyncio.gather()` 并发等待多个 Task。

### Q9: 协程中如何避免阻塞事件循环？

**绝对不能**在协程中调用同步阻塞函数（如 `time.sleep()`、`requests.get()`），否则会卡住整个事件循环。

```python
# 错误示范：会阻塞整个事件循环
async def bad():
    time.sleep(5)  # 整个事件循环停摆 5 秒

# 正确做法 1：用异步版本替代
async def good():
    await asyncio.sleep(5)  # 不阻塞

# 正确做法 2：把阻塞调用丢到线程池
async def also_good():
    loop = asyncio.get_running_loop()
    result = await loop.run_in_executor(None, time.sleep, 5)

# 正确做法 3：用 aiohttp 替代 requests
# pip install aiohttp
import aiohttp
async def fetch(url):
    async with aiohttp.ClientSession() as session:
        async with session.get(url) as resp:
            return await resp.text()
```

## I/O 多路复用

### Q10: select、poll、epoll 的区别？

三者都是 I/O 多路复用机制，让单个线程同时监控多个文件描述符（socket）的就绪状态。

| | select | poll | epoll |
|------|--------|------|-------|
| 连接数限制 | 默认 1024 | 无限制 | 无限制 |
| 查找方式 | 遍历所有 fd | 遍历所有 fd | 回调通知（O(1)） |
| 数据拷贝 | 每次全量拷贝 fd_set | 每次全量拷贝 | 只拷贝就绪的 fd |
| 触发方式 | 水平触发 | 水平触发 | 水平触发 + 边沿触发 |
| 适用场景 | 连接少 | 中等 | 大规模高并发 |

**select 的问题**：

1. 单个进程能监控的 fd 有上限（FD_SETSIZE = 1024）
2. 每次调用都要把 fd_set 从用户态拷贝到内核态
3. 内核需要遍历所有 fd 找到就绪的，O(n) 复杂度

**epoll 的改进**：

1. 用红黑树维护注册的 fd，无数量限制
2. 事件驱动——fd 就绪时通过回调加入就绪链表，不用遍历
3. 只需拷贝就绪的 fd 到用户态

```python
import selectors  # Python 3.4+ 推荐的高层封装

sel = selectors.DefaultSelector()  # Linux 自动选 epoll

def accept(sock, mask):
    conn, addr = sock.accept()
    sel.register(conn, selectors.EVENT_READ, read)

def read(conn, mask):
    data = conn.recv(1024)
    if data:
        conn.send(data)  # echo
    else:
        sel.unregister(conn)
        conn.close()
```

### Q11: 边沿触发（ET）和水平触发（LT）的区别？

| | 水平触发（LT） | 边沿触发（ET） |
|------|---------------|---------------|
| 通知时机 | 只要缓冲区有数据就通知 | 只在缓冲区状态变化时通知一次 |
| 漏读后果 | 下次还会通知 | 永远丢失（直到新数据到达） |
| 编程复杂度 | 简单 | 需要循环读直到 EAGAIN |
| 适用场景 | 一般场景 | 高并发追求极致性能 |

```python
# ET 模式下必须循环读取
import socket, errno

def handle_et(conn):
    while True:
        try:
            data = conn.recv(1024)
            if not data:
                break
            process(data)
        except BlockingIOError as e:  # EAGAIN
            break  # 缓冲区已空
```
