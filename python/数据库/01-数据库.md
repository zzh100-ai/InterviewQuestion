## 事务与隔离级别

### Q1: 什么是事务？ACID 分别代表什么？

事务是一组操作的集合，要么全部执行成功，要么全部不执行。

| 特性 | 说明 | 实现方式 |
|------|------|----------|
| **A** 原子性 | 事务是最小执行单元，不可分割 | undo log 回滚 |
| **C** 一致性 | 事务前后数据满足所有约束 | 由其他三个特性共同保证 |
| **I** 隔离性 | 并发事务间互不干扰 | 锁 + MVCC |
| **D** 持久性 | 提交后数据永久保存 | redo log |

```sql
START TRANSACTION;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
UPDATE accounts SET balance = balance + 100 WHERE id = 2;
COMMIT;
-- 如果任何一步失败，整体 ROLLBACK
```

### Q2: 数据库有哪些隔离级别？各解决了什么问题？

| 隔离级别 | 脏读 | 不可重复读 | 幻读 |
|----------|------|------------|------|
| READ UNCOMMITTED | ✗ | ✗ | ✗ |
| READ COMMITTED | ✓ | ✗ | ✗ |
| REPEATABLE READ（MySQL 默认） | ✓ | ✓ | ✓* |
| SERIALIZABLE | ✓ | ✓ | ✓ |

- **脏读**：读到其他事务未提交的修改
- **不可重复读**：同一事务内两次读同一数据，结果不同（别的事务 update 了）
- **幻读**：同一事务内两次查询范围，结果条数不同（别的事务 insert 了）

> MySQL InnoDB 的 REPEATABLE READ 通过 Next-Key Lock（行锁 + 间隙锁）解决了幻读问题。

```sql
-- 查看当前隔离级别
SELECT @@transaction_isolation;

-- 设置隔离级别
SET SESSION TRANSACTION ISOLATION LEVEL READ COMMITTED;
```

## 索引原理与优化

### Q3: 什么是索引？B+Tree 索引为什么是 MySQL 默认选择？

索引是帮助数据库高效获取数据的**排好序的数据结构**。没有索引时查询需要全表扫描 O(n)，有索引时可以通过 B+Tree 在 O(log n) 内定位目标行。

**B+Tree 相比 B-Tree 的优势**：
1. **非叶子节点不存储数据**，只存索引键，因此一个节点能存更多键，树更矮，磁盘 I/O 次数更少
2. **叶子节点形成有序链表**，范围查询只需在叶子节点间顺序遍历，效率极高
3. **查询更稳定**：所有值都在叶子层，每次查询路径长度相同

```
          [5,  10]          ← 非叶子节点（只存索引）
         /    |    \
    [1,3]  [6,8]  [12,15]   ← 叶子节点（存完整数据，链表相连）
```

```sql
-- 创建普通索引
CREATE INDEX idx_name ON users(name);

-- 联合索引（注意最左前缀原则）
CREATE INDEX idx_a_b_c ON orders(user_id, status, create_time);
```

### Q4: 什么是聚集索引和非聚集索引？

| | 聚集索引 | 非聚集索引（二级索引） |
|------|----------|------------------------|
| 数据存储 | 叶子节点就是数据行本身 | 叶子节点存聚集索引的 key |
| 数量限制 | 每表只有一个 | 可以有多个 |
| 查询路径 | 一次定位 | 需要**回表**查聚集索引 |
| 默认 | InnoDB 用主键建聚集索引 | — |

**回表**：非聚集索引找到主键 id 后，还要去聚集索引查一次才能拿到完整行数据。如果查询的列都在二级索引中则不需要回表，这称为**覆盖索引**。

```sql
-- 覆盖索引：name 和 age 都在索引中，不需要回表
CREATE INDEX idx_name_age ON users(name, age);
SELECT name, age FROM users WHERE name = '张三';
```

### Q5: 什么是最左前缀原则？

联合索引中，查询条件必须从索引的最左列开始匹配，且不能跳过中间列。索引的列顺序决定了有哪些查询能用到该索引。

```sql
-- 联合索引 (a, b, c)
CREATE INDEX idx_abc ON t(a, b, c);

-- 能用到索引的查询：
WHERE a = 1;                    -- 用 a
WHERE a = 1 AND b = 2;          -- 用 a, b
WHERE a = 1 AND b = 2 AND c = 3;-- 用 a, b, c
WHERE a = 1 AND c = 3;          -- 只用到 a（跳过了 b）

-- 用不到索引的查询：
WHERE b = 2;                    -- 没有最左列 a
WHERE c = 3;                    -- 没有最左列 a
```

**索引优化建议**：
- 把区分度高的列放在联合索引前面
- 范围查询的列放在联合索引最后（范围之后的其他列用不上索引）
- `ORDER BY` 的列也考虑加入索引

## MySQL 引擎对比

### Q6: InnoDB 和 MyISAM 有什么区别？

| 特性 | InnoDB | MyISAM |
|------|--------|--------|
| 事务支持 | ✓ | ✗ |
| 行级锁 | ✓ | ✗（表锁） |
| 外键 | ✓ | ✗ |
| MVCC | ✓ | ✗ |
| 崩溃恢复 | redo log | 需手动修复 |
| 全文索引 | 5.6+ 支持 | ✓ |
| COUNT(*) | 需扫描 | 有单独计数器（快） |
| 数据存储 | 表空间（.ibd） | 独立文件（.MYD/.MYI） |

**选择建议**：绝大多数场景用 InnoDB。MyISAM 适用于只读或极少更新的日志/归档场景，但现在基本被 InnoDB 替代。

### Q7: 如何对 SQL 进行 EXPLAIN 分析？

```sql
EXPLAIN SELECT * FROM orders WHERE user_id = 100;
```

重点关注字段：

| 字段 | 含义 |
|------|------|
| **type** | 访问类型：system > const > eq_ref > ref > range > index > ALL（ALL 是噩梦） |
| **key** | 实际使用的索引 |
| **rows** | 预估扫描行数 |
| **Extra** | Using index（覆盖索引，好）、Using filesort（需额外排序，差）、Using temporary（临时表，很差） |

```sql
-- 常见优化场景
-- 1. type 是 ALL → 加索引
-- 2. Extra 有 Using filesort → 调整 ORDER BY 列的索引
-- 3. Extra 有 Using temporary → 优化 GROUP BY / DISTINCT
```

## 并发控制与锁

### Q8: 乐观锁和悲观锁有什么区别？

| | 悲观锁 | 乐观锁 |
|------|--------|--------|
| 策略 | 认为冲突一定会发生 | 认为冲突很少发生 |
| 实现 | SELECT ... FOR UPDATE | 版本号 / CAS |
| 适用场景 | 写多、冲突激烈 | 读多、冲突少 |
| 代价 | 锁等待、死锁风险 | 重试开销 |

**悲观锁**：

```sql
START TRANSACTION;
SELECT stock FROM products WHERE id = 1 FOR UPDATE;
-- 如果 stock >= 1 才执行扣减
UPDATE products SET stock = stock - 1 WHERE id = 1;
COMMIT;
```

**乐观锁**：

```sql
-- 更新时检查版本号
UPDATE products
SET stock = stock - 1, version = version + 1
WHERE id = 1 AND version = 3;
-- 影响行数 = 0 说明版本号被其他事务改了，需要重试
```

### Q9: 什么是 MVCC？InnoDB 如何实现 MVCC？

MVCC（Multi-Version Concurrency Control）通过保存数据的多个历史版本，让读操作不需要加锁也能读到一致的数据，极大地提高了并发性能。

**InnoDB 的实现**：
- 每条记录隐含两个字段：`创建版本号` 和 `删除版本号`
- 每开始一个事务时分配一个递增的事务 ID
- SELECT 只读到创建版本 ≤ 当前事务 ID 且（删除版本 > 当前事务 ID 或为空）的记录
- UPDATE 实际是：标记旧版本删除 + 插入新版本
- DELETE 实际是：标记删除版本号
- 旧版本由 purge 线程异步清理

```sql
-- READ COMMITTED：每次查询生成新的 ReadView
-- REPEATABLE READ：事务开始时生成 ReadView，整个事务用同一个
```

## Redis 基础

### Q10: Redis 有哪些常用数据结构？各自适用场景？

| 数据类型 | 底层实现 | 适用场景 |
|----------|----------|----------|
| **String** | SDS（简单动态字符串） | 缓存、计数器、分布式锁 |
| **Hash** | ziplist / hashtable | 存储对象（用户信息等） |
| **List** | quicklist（ziplist + linkedlist） | 消息队列、最新列表 |
| **Set** | intset / hashtable | 标签、共同好友、去重 |
| **ZSet** | ziplist / skiplist | 排行榜、延迟队列（按分数排序） |
| **Bitmap** | String 的位操作 | 签到统计、布隆过滤器 |
| **HyperLogLog** | 概率算法 | UV 统计（误差 0.81%） |

```python
import redis
r = redis.Redis()

# String：缓存 + 过期
r.setex("user:1001", 3600, json.dumps(user_data))

# ZSet：排行榜
r.zadd("leaderboard", {"user_a": 100, "user_b": 200})
r.zrevrange("leaderboard", 0, 9, withscores=True)  # Top 10

# List：消息队列（LPUSH + BRPOP）
r.lpush("task_queue", task_json)
task = r.brpop("task_queue", timeout=5)
```

### Q11: Redis 持久化方式 RDB 和 AOF 有什么区别？

| | RDB | AOF |
|------|-----|-----|
| 原理 | 定时快照，把内存数据存为二进制文件 | 记录每条写命令到日志 |
| 文件大小 | 小（压缩的二进制） | 大（文本命令，可 rewrite） |
| 恢复速度 | 快 | 慢（重放命令） |
| 数据安全 | 可能丢几分钟数据 | 可配置每秒 fsync，丢 1 秒 |
| 适用场景 | 备份、灾备 | 数据安全性要求高 |

**生产环境通常同时开启**：用 AOF 保证数据安全，用 RDB 做灾备和快速恢复。

### Q12: 缓存雪崩、缓存穿透、缓存击穿如何解决？

| 问题 | 描述 | 解决方案 |
|------|------|----------|
| **缓存雪崩** | 大量缓存同时过期，请求全压到数据库 | 过期时间加随机值、多级缓存、限流降级 |
| **缓存穿透** | 查不存在的数据，缓存不生效，一直查库 | 缓存空值、布隆过滤器 |
| **缓存击穿** | 热点 key 过期瞬间，大量请求打穿缓存 | 互斥锁、逻辑过期（永不过期+异步刷新） |

```python
# 缓存穿透：缓存空值
def get_user(user_id):
    cache_key = f"user:{user_id}"
    data = redis.get(cache_key)
    if data is not None:
        return json.loads(data) if data != "NULL" else None
    user = db.query(user_id)
    if user:
        redis.setex(cache_key, 3600, json.dumps(user))
    else:
        redis.setex(cache_key, 300, "NULL")  # 缓存空值，防止穿透
    return user

# 缓存雪崩：随机过期时间
import random
ttl = 3600 + random.randint(0, 600)  # 1h ~ 1h10min
redis.setex(key, ttl, value)
```
